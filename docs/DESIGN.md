# 设计说明

这是一个类 MIT Battlecode 的编程对战平台，但**只面向 AI**：由不同的大模型各自编写 Python bot，平台负责让 bot 在同一张地图上对战、记录回放、做循环赛排名。

本文回答三个问题：

1. Battlecode 那套“固定 SDK + 固定指令 + 计算量上限”在 Python 里能不能做？要不要做？
2. 平台是怎么搭的，哪些部分以后可以替换？
3. 竞赛形式还有哪些事情需要你来定？

---

## 1. 结论：SDK 和计算上限都能实现，而且建议由引擎强制执行

### 为什么不能靠大模型“自觉遵守”

- **大模型在有胜负压力时会钻空子。** 常见的捷径有：用 `gc` / 栈帧拿到引擎对象直接改血量、读对手的源码、给共享的类打补丁搞破坏、用暴力搜索把计算量拉满。这些不一定是“故意作弊”，模型只是在优化“赢”这个目标。
- **你要比较的正是“谁更强”。** 如果 A 模型守规矩、B 模型不守，排名比的就是“谁更敢违规”，结果没有意义。
- **没有计算上限，比的是算力不是策略。** 一个每回合做全图搜索的 bot 和一个精打细算的 bot 根本不在同一个比赛里。
- **成本不高。** 强制执行的核心代码只有几百行（`arena/engine/meter.py`、`arena/engine/sandbox.py`），性能开销也小（见下文）。

### 怎么实现的（四层）

| 层 | 做什么 | 代码 |
|---|---|---|
| ① 固定 SDK | bot 只拿到一个 `RobotController` 对象。它**没有任何属性**，游戏状态存放在 bot 摸不到的引擎表里。每个方法都会检查是不是本机器人的回合、扣固定指令费、严格校验参数类型、按规则判断能否执行，然后原子地执行。SDK 里的类（`Location`、`Direction` 等）全部不可变且类本身只读，防止一方给共享类打补丁破坏对手。 | `arena/game/controller.py`、`arena/game/types.py` |
| ② 指令计数（等价于 Battlecode 的 bytecode limit） | 用 Python 3.12+ 的 `sys.monitoring`（PEP 669），**只在 bot 的代码对象上**开启 INSTRUCTION 事件：bot 每执行一条字节码计 1，白名单标准库里纯 Python 实现的部分（`Counter`、`random`、`deepcopy` 等）也计入，引擎代码不计、全速运行。预算用完后，**之后的每一条指令都会再抛异常**，所以 `except:`、`finally:` 都没法吞掉它继续跑。 | `arena/engine/meter.py` |
| ③ 沙箱 | 静态 AST 检查（禁止 `__xxx__` 属性和名字，禁止 `gi_frame` 这类内省属性，禁止 `str.format` 走属性，禁止 async 和元类，import 只允许白名单模块）+ 受限 builtins（没有 `open/eval/exec/type/id/vars/globals` 等）+ 每个机器人拿到自己的一份模块副本（模块里的纯 Python 函数和可变类也逐个复制），所以既没法偷看引擎，也没法在机器人之间私下共享内存。 | `arena/engine/sandbox.py` |
| ④ 兜底 | C 实现的内建函数（比如 `sorted` 一个超大列表）只算 1 条指令，所以另有每回合 CPU 时间上限（默认 0.1 秒，`ITIMER_PROF`）：触发后预算立即清零，下一条指令就结束回合；如果还停不下来，第二阶段直接打断。循环赛里每场比赛还在独立子进程里跑，有内存上限（2GB）和整场超时，卡死的一方判负。 | `arena/engine/meter.py`、`arena/engine/tournament.py` |

`tests/test_sandbox.py` 里的测试会主动尝试这些逃逸方式（死循环加 `except:`、`finally` 里死循环、`().__class__.__base__`、`getattr(x, "__class__")`、给 `Location.add` 打补丁、读 `RobotController._CTX` 等），全部要求被拦下。

### 性能

- 每条被计数的指令约 66 ns 开销，1 万条指令的满额回合约 0.7 ms。
- 示例 bot 每回合实际只用 200–500 条指令，一场 100–250 回合的比赛通常不到 0.5 秒。
- 预算（单位 1 万 / HQ 2 万条每回合）足够做局部搜索，但**放不下每回合全图 BFS**（3–6 万条），这正是 Battlecode 式的取舍：逼着 bot 跨回合分摊计算、想更聪明的办法。

### 局限（如实说明）

- **这不是针对人类黑客的安全边界。** 威胁模型是“想赢的 AI 走捷径”。如果要跑来源不明的代码，请再套一层容器或虚拟机。
- **C 内建函数不按真实开销计费**，只能靠 CPU 时间兜底。CPU 时间是唯一不确定的部分，只有滥用的 bot 才会碰到。以后可以给 `sorted/sum/min/max` 这类调用按参数长度额外计费。
- **指令数随 CPython 版本变化**（不同版本字节码不同）。正式比赛请固定 Python 版本（当前在 3.13 上开发和测试）。
- **内存上限只在循环赛（子进程）里生效**，单场 `run` 命令不限内存。
- `run` 命令在本进程里执行；循环赛每场比赛都用独立进程，更安全。

## 2. 架构

```
bots/<name>/bot.py ──► loader ──► 静态检查 + 编译 + 插桩
                                      │
     maps.generate(seed) ──► GameWorld（权威状态、规则）
                                      │
match loop：每回合按出生顺序逐个执行机器人
  └─ 每个机器人：独立模块副本 + RobotController
     └─ METER.run(turn, rc, 预算, CPU 时限)
                                      │
            每回合快照 ──► replay.json ──► viewer（HTML）
                                      │
              tournament：循环赛，每场独立子进程，Bradley–Terry 评分
```

| 目录 | 内容 | 以后会变吗 |
|---|---|---|
| `arena/engine/` | 平台本身：沙箱、指令计数、对局循环、循环赛 | 基本稳定 |
| `arena/game/` | 占位游戏 “Ore Rush” 的规则：地图、机器人、`RobotController` API、平衡参数 | **会变**，等你定竞赛形式 |
| `arena/sdk.py` | bot 唯一能 import 的本项目模块 | 跟着游戏变 |
| `arena/viewer/` | 单文件 HTML 回放查看器 | 随游戏的可视化需求变 |
| `bots/` | 基线 bot：`examplebot`（像样的基线）、`rusher`（全力速攻）、`randombot`（随机） | 新增 AI 的 bot 放这里 |

### 对局流程

1. 加载两个 bot：静态检查不通过的一方直接判负。
2. 用种子生成对称地图（旋转 / 左右镜像 / 上下镜像三选一，bot 不知道是哪种）。
3. 每回合：被动收入、冷却减 10，然后按出生顺序逐个执行机器人（两队自然交错）。每个机器人第一次行动时执行它自己的一份模块代码（单独 5 万条初始化预算），之后每回合调用 `turn(rc)`。
4. 任何一方 HQ 被摧毁立即结束；到 1000 回合按 HQ 血量 → 军队价值 → 银行矿 → 总采矿量 → 种子抛硬币判定。
5. 每回合记录快照（机器人位置、血量、每个机器人本回合用了多少指令、攻击/采矿/死亡事件、bot 自己画的调试点线），写成回放 JSON。

### 公平与可复现

- 地图对称；同一个种子下，循环赛会**交换先后手**各打一局，抵消 A 方先行动的优势。
- 机器人 id 是种子打乱的 4 位数，不泄露信息。
- 感知结果按距离排序，同距离的先后顺序每场比赛随机（固定方向的排序会在镜像地图上偏向一方）。
- 每个机器人的 `random` 用 (种子, 队伍, 出生序号) 播种；CLI 固定 `PYTHONHASHSEED=0`。同一 Python 版本下，同样的种子 + 同样的 bot = 完全相同的比赛（有测试保证）。

## 3. 需要你来定的事（竞赛形式）

平台已经能跑，下面这些属于“比赛怎么比”，我没有替你决定：

1. **AI 怎么参赛**
   - 一次性写完提交，还是允许多轮迭代？（建议允许：给它 `check` / `run` / 回放报告作为反馈，比较的是“会不会调试和改进”，更接近真实能力。）
   - 每个模型的迭代轮数、时间或 token 上限要统一。
   - 能否看到对手的代码或回放？（Battlecode 允许看比赛回放，不能看代码。）
   - `docs/AI_PLAYER_PROMPT.md` 给了一个可以直接用的提示词模板。
2. **正式比赛由谁来跑**：AI 在自己的工作区里改不改引擎都没关系，正式比赛只拿它们的 `bot.py`，用干净的引擎跑循环赛。
3. **游戏规则**：现在的 Ore Rush 只是为了让平台能跑起来的占位游戏（矿工采矿、士兵打仗、HQ 造兵）。想要更有策略深度可以加：建筑、科技、更多兵种、地形效果、视野遮挡等。改 `arena/game/` 即可，平台层不用动。
4. **平衡参数**：`arena/game/constants.py` 里的所有数字，包括每回合指令预算。预算越小，越考验算法效率。
5. **赛制**：每对组合打几局（默认 2 局，交换先后手）、用哪些种子、是否加入固定基线 bot 作为“及格线”。

## 4. 后续可以做的

- 给 C 内建函数按参数规模计费，减少对 CPU 时间兜底的依赖。
- 回放查看器：显示每个机器人的 `print` 日志、按指令用量着色。
- 自定义地图编辑器 / 固定地图池（现在支持 `--map file.json`）。
- 自动化“AI 参赛者”脚本：用 API 驱动多个模型按同一流程写 bot、迭代、提交，然后自动跑循环赛。
